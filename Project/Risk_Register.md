# Risk Register

| Risk ID | Risk Description | Possible Cause | Probability | Impact | Mitigation/Response Strategy |
|---|---|---|---|---|---|
| R1 | The rules for how rental applications and viewings work are not clearly defined, so features are built one way and later have to be redone later | Open questions such as whether a tenant can apply to several properties at once, what happens to a listing after an application is accepted, and who can cancel or reschedule a viewing, the team's answers may change as the project develops | High | High | Before starting the database, define the application process clearly using states like submitted, under review, accepted, rejected, and withdrawn. Put the booking and cancellation rules in Scope.md and confirm them with the instructor first. If anything changes later, record it in the repository with a clear commit message. If a change comes up, check which screens and database tables it will affect and plan it for the next iteration instead of making a quick patch right away. |
| R2 | Core features like property search, viewing scheduling, and document uploads may not work properly. | Possible issues include two users trying to book the same viewing slot, search becoming complicated when multiple filters like location, price, and size are used, and problems with uploading different file types. | Medium | Medium | Start by building and testing the most difficult features. Make sure the database prevents the same viewing slot from being booked twice. Create test cases for situations like two people booking at the same time, cancellations, and searches with no results. If it occurs, release a simpler working version first, such as having owners approve bookings instead of allowing instant bookings, and improve it in the next iteration. |
| R3 | Some features or deliverables may not be finished on time. | This could happen because the amount of work was underestimated, technical problems from R2 take longer than expected, or other university work takes up development time. | Medium | High | Focus on the most important features first, including property listings, search, viewing bookings, and online applications. Check the team's progress every week. If we see that time becomes limited we will remove lower priority features instead of delaying the final submission. If so we can move non essential features to a later release. |
| R4 | Tenant information could be exposed or accessed by the wrong person. | Applications may contain personal information such as contact details, ID copies, and income documents. Weak login security or poor access control could also allow users to see information they should not have access to. | Medium | High | Use different access levels for tenants, owners, and administrators. Passwords should be securely hashed, and uploaded files should be checked for their type and size. Only collect information that is actually needed. Use fake data when testing instead of real people's documents. If it occurs temporarily disable the affected feature, fix the security issue, test it again, and remove any exposed data. |
| R5 | The team may not be able to get feedback from real tenants or property owners. | There may not be an actual client available, and landlords or property managers may be difficult to contact during the semester. | High | Low | Use the instructor as a substitute stakeholder for feedback on requirements and design. We can also ask students and our parents who have experience renting or searching for housing about their experiences. Before finalizing the design, test the prototype using realistic tenant and owner scenarios. |
