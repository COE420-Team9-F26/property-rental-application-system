# Software Process Model
## Model
Unified Process (UP)

## Justification

Our project, the Property Viewing and Rental Application System, is modeled, not implemented, across the semester. Each lab builds out one part of the system's design, working toward a complete picture of the system rather than a finished, working product. UP is built around this idea. It organizes work into phases, which lines up well with our labs.

This is far better than the alternatives. Scrum and the Incremental model both center on delivering working software increments, which doesn't apply since we have no implementation phase. Waterfall is too rigid for a process that explicitly revisits and refines phases lab over lab. Spiral is justified for large, high risk, expensive systems, which is not the case for us. UP's iterative approach is the closest  to what we're actually doing.

## Overheads and Mitigation

UP is typically criticized for being heavy on documentation and difficult for small teams to sustain. For our project this is less of a drawback, since we are actually only focusing on documentation, not a live system. To keep the workload manageable across our team of 4.
We split each lab's documents by parts, so no one carries the full load.
Keep the shared repo organized with clear commits, so documents stay consistent instead of duplicated.
Review each other's work at the start of each lab to catch issues early.
