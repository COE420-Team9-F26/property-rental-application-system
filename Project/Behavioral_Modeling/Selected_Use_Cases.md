# Selected Use Cases


| Use Case ID | Use Case Name | Primary Actor | Purpose | Reason for Selection |
|---|---|---|---|---|
| UC-08 | Book Viewing Appointment | Tenant | The tenant picks one of the available viewing time slots of a listing. The system reserves the slot, creates a confirmed viewing appointment and sends a confirmation notification to both the tenant and the landlord (FR-08, FR-13, S-03). | Core scheduling function of the system (process P4). It includes UC-14 Log Into System (R-02). It gives a natural iteration (going through the listing's available slots and notifying both parties) and a guard that blocks double booking of a slot (FR-13). The classes already exist in the Lab 5 Class Diagram: Tenant, PropertyListing, ViewingSlot, ViewingAppointment and Notification. |
| UC-09 | Submit Rental Application | Tenant | The tenant submits his or her occupation, number of occupants and desired move-in date for a listing. The system creates a rental application with the status SUBMITTED (FR-09, FR-10, S-04). | Main outcome of the tenant journey (process P5). It includes UC-14 Log Into System (R-01). It has two clear guards: the listing must be accepting applications, and the tenant must not already have an active application for the same listing (FR-10). The classes are Tenant, PropertyListing and RentalApplication. |
| UC-05 | Review Rental Application | Landlord | The landlord goes through the applications received for his or her listings and accepts or rejects one. The system updates the application status and, when an application is accepted, closes the listing to new applications (FR-05, S-04). | The landlord side of scenario S-04, so it completes the flow started by UC-09. It adds a different actor and an accept or reject choice to the set. It has an iteration over the received applications and a guard that only an application with the status SUBMITTED can be decided (FR-05). The classes are Landlord, PropertyListing and RentalApplication. |
